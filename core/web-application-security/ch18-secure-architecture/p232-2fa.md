# Two-Factor Authentication (2FA)
(Source: PDF p. 232, with the rest of the section on PDF p. 233 above the PII heading)

## What the section covers
Why an application that already hashes passwords and encrypts traffic should also offer two-factor authentication, how it is delivered, and what it does and does not stop.

## Meaning and role
- In addition to secure, hashed passwords encrypted in transit, the application should offer 2FA to users who want to protect their accounts (PDF p. 232).
- Figure 18-2 shows Google Authenticator, one of the most common 2FA apps for Android and iOS. It works with many websites and has an open API for integrating with an application.
- The book calls 2FA a fantastic security feature that works very well on a simple principle.

## How it works
- Most 2FA systems ask the user to enter a password in the browser and also a code generated by a mobile app or sent by SMS text message. These details are printed on the next page and carry no page cite here.
- More advanced protocols use a physical hardware token, usually a USB drive that creates a one-time token when plugged into the user's computer. Physical tokens suit a company's employees better than its customers, since handing out and managing tokens for an ecommerce platform would be painful.

## Strength and limits
- Phone app or SMS 2FA is not as secure as a dedicated USB token but is still an order of magnitude safer than no 2FA.
- Provided the 2FA app or messaging protocol has no vulnerability, 2FA removes remote logins that the account owner did not start. To compromise such an account an attacker needs both the account password and the physical device holding the codes, usually a phone.

## Decision for the example
During the architecture review for MegaMerch the author strongly suggests offering 2FA to users who want better account security.
