# Phase 1 - Design and Analysis
(Source: PDF p. 64. The text above the "Phase 1" heading on this page is the chapter introduction, WS-C05-001.)

## What the section covers
The first SDLC phase: deciding what code to write before writing any, with the role of requirements and issue-tracking software (PDF p. 64).

## Meaning
- The SDLC begins with thinking about what to build, not with coding. In design and analysis you study the features to add and plan their implementation (PDF p. 64).
- Early in a project this may be only a few sketched design aims. Once a site is live it needs more deliberation, because changes must not break functionality existing users rely on (PDF p. 64).

## How it works
- The most important aim is to pin down the requirements the code must meet, so that when the team finishes everyone can judge whether the changes truly meet them (PDF p. 64).
- Client work means meeting stakeholders and getting agreement on a list of goals. In-house work mainly means developing and documenting a shared vision of what is being built (PDF p. 64).
- Issue-tracking software (also called bug trackers) helps a great deal, especially when diagnosing and fixing bugs on an existing site. It records each development goal as an issue, for instance "build a customer checkout page" or "fix the spelling mistake on the home page". Issues are assigned to developers, who prioritise them, write code and mark them done. Developers can attach the specific code changes that fix a bug or add a feature to the issue. On large teams, managers can schedule issues with project management software for reporting (PDF p. 64).

## When and how to apply
How much planning to do before coding varies. Teams making firmware or critical systems such as nuclear reactors spend a lot of time designing because they rarely get to fix code after deployment. Web developers tend to move faster (PDF p. 64).
