# Evaluation execution (choose methods, build a small set, run, interpret, audit the evaluation itself)

## When to use
Use when the task is to judge the quality of an AI system's outputs, to compare two models, prompts or configurations, or to check whether an existing evaluation can be trusted. It complements the planning workflow `../architect/eval-plan.md`. Model calls cost money: nothing in this workflow runs a paid call without the user's approval and a stated spend cap, and nothing runs against production.

## Inputs needed
From discovery (`../discovery.md`, Evaluation row): existing eval folders, golden sets, metric code, judge calls, test runners. Ask only for what is missing (`../architect/intake.md`): the task and what a good output is; whether real or anonymised production examples may be used; whether a way to call the system under test from a command line exists; the spend cap and approval to run; whether logprobs are available for the model. If the user cannot say what "good" means, stop at step 3 and help write the guideline first.

## Procedure
1. **Decompose the system.** List the components and, for each, the output that can be checked on its own (the book's example: PDF-to-text scored by similarity to ground-truth text, employer extraction scored by accuracy on correct text). Evaluate the end-to-end output and each intermediate output independently, per turn and, where tasks span turns, per task including number of turns. Task boundaries are hard to determine; state the rule you used. `[C04-011]`
2. **Read or write the guideline.** Required: what the application should do and should not do (out-of-scope inputs and the expected response), criteria (for example relevance, factual consistency, safety), a scoring system per criterion (binary, 1 to 5, 0 to 1, or -1/0/1 entailment), a rubric with an example of each score, human validation of the rubric, a minimum usefulness threshold, and a mapping of metric levels to the business outcome. The book's numbers (for example factual consistency of at least 50%, or 80/90/98% automating 30/50/90% of requests) are illustrations: the threshold and the mapping come from the user's business, never from this workflow. Missing guideline is the first finding. `[C04-012]`
3. **Pick a method per criterion.** Use the first applicable row; mix methods when cost requires.

   | Situation | Method | Notes |
   |---|---|---|
   | Output can be executed or checked mechanically (code, SQL, measurable objective) | Functional correctness: run tests, report pass rate, or pass@k (a problem counts if any of k samples passes, so report pass@1 when the product serves one answer). The book notes it is not always measurable or automatable; INTERPRETATION: it is only as strong as the test cases | `[C03-010]` |
   | Short exact answers | Exact match, or contains-reference with the false-accept risk checked | `[C03-011]` |
   | Free text with good references | Lexical similarity (overlap, edit distance, n-gram) only if references are comprehensive and correct, and not as a proxy for correctness (the book cites BLEU failing to separate correct from incorrect code); otherwise semantic similarity on embeddings, whose reliability depends on the embedding model and which costs compute | `[C03-011]`, `[C03-012]` |
   | No references, subjective or flexible criteria, production use | AI judge, with the limits in step 7; a narrow criterion such as toxicity may use a small specialised classifier instead | `[C03-014]`, `[C04-013]` |
   | Choosing between candidates, or output quality is hard to score absolutely | Comparative evaluation with a judge or humans | `[C03-020]` |
   | Classification with probabilities available | Logprobs as confidence | `[C04-013]` |
   | Model-level fit or contamination screening | Language-model metrics (step 4) | `[C03-008]` |

   Mixing example from the book: a cheap classifier on all data plus an expensive judge on a small share. Use automatic metrics as far as possible but keep human evaluation, including in production. `[C04-013]`
4. **Use language-model metrics only where they apply.** They need token probabilities, so check whether the model exposes logprobs; many commercial models do not. `[C03-008]` Cross entropy, perplexity, bits-per-character and bits-per-byte are variants of one idea: lower is a better prediction. `[C03-004]`, `[C03-005]` Never compare bits per token across models with different tokenisation; use bits-per-byte or character-based figures, and state the unit (bits or nats) because frameworks differ. `[C03-006]`, `[C03-007]` Perplexity depends on data structure, vocabulary size and context length, so compare only like with like. Perplexity may be a poor proxy for a post-trained (instruction-tuned or preference-tuned) or quantised model. Legitimate uses here: screening a benchmark for likely contamination (unusually low perplexity), and flagging abnormal inputs (unusually high). `[C03-008]` These metrics do not measure whether an application works; do not report them as application quality.
5. **Build a small evaluation set.** Prefer real production examples (anonymised, with user approval) and natural labels; otherwise label by humans or AI with human review. Cover every component and criterion. Keep separate slices: the production-like distribution for the overall number, slices by tier or source, cases where the system often errs, cases where users often err (typos), and an out-of-scope set. Size: large enough to be reliable, small enough to run. The book's guide for 95% confidence that one system is better: a 30% difference needs about 10 samples, 10% about 100, 3% about 1,000, 1% about 10,000; every 3x smaller difference needs 10x the samples. These are OpenAI's rough guide, since the book says exact sample sizes need a score distribution that is rarely known. Benchmarks in one reference harness have a median of about 1,000 examples; the organizers of one prize called 300 an absolute minimum and preferred at least 1,000. If the user only has fewer, run it and label results as indicative. `[C04-013]`
6. **Run, with approval and a cap.** Write a runner (a throwaway script in the run's scratch folder, not in the skill folder) that sends each example to the system under test and the scorer and writes one result file. Execute it only through `python scripts/run_check.py --case EV-<n> --evidence-dir <run>/evidence --timeout <s> -- <command>`. Before running: estimate calls times cost (generation plus every judge prompt; the book's example is that a judge on every response roughly doubles calls with one judge prompt and quadruples them with three, and few-shot examples in the judge prompt raised one study's spend about fourfold), compare to the cap, get approval, record the approval words. Stop at the cap and report partial results as such. `[C03-016]`
7. **Apply the judge rules when a judge is used.** The judge is a system of model, prompt and sampling settings; pin and record all three. Prompt must state task, criteria, scoring system and scored examples; prefer classification or a small discrete scale (typically 1 to 5; the book reports wider ranges do worse) over continuous. A judge can score one response, compare a response with a reference (an alternative to similarity metrics), or pick the better of two. `[C03-015]` Known weaknesses: score varies between runs and wordings, high consistency is not accuracy, criteria are not standardised across tools, a changed judge breaks trend comparison, self-bias (a model favours its own output), first-position bias (randomise order and repeat), verbosity bias (compare scores against length), cost and latency, and data sent to a proprietary judge. Never trust a judge whose model and prompt cannot be seen. Supplement with exact metrics or human review. `[C03-016]` Choose the judge by need: stronger than the judged model for rigor, applied to a sampled subset if cost matters; the same model only for sanity checks; a weaker judge is an open question; a small specialised judge (reward, reference-based or preference model) where the judgment is narrow. `[C03-017]` Rule for findings: any finding resting only on a judge is capped at `probable`. `[C03-016]`
8. **Comparative runs.** For A versus B, show both outputs in randomised order to humans or a judge, allow ties, and report win rate with the number of matches. INTERPRETATION: do not use preference voting where correctness decides the answer or where the voter cannot judge (the book notes volunteers may not fact-check and may click at random). Comparison also scales badly: pairs grow quadratically with models, and crowd votes are not standardised. Remember limits: transitivity may not hold, public crowd votes lack standardisation and use simple prompts, and a win rate does not say whether either model is good enough, so pair it with a pointwise result on the same task (for example 51% wins versus a 70% resolution rate cannot be converted). `[C03-019]` Comparison is still the right tool when absolute scoring is hard, since it targets human preference and cannot be saturated or trained on easily. `[C03-020]`
9. **Interpret.** Report per slice as well as overall, with counts. A model can win every slice and lose overall (Simpson's paradox) when slice sizes differ; check before declaring a winner. Compare each metric with the usefulness threshold from step 2, then say what the level means for the business. `[C04-013]`, `[C04-012]`
10. **Audit the evaluation itself.** Questions: do better responses get higher scores; is it reproducible (rerun and compare; for a judge use temperature 0 and a fixed configuration); what is the variance across sets and bootstrap resamples (draw with replacement from a set of 100 many times; if results swing from 90% to 70%, the set is too small); are metrics so correlated that one is redundant, or uncorrelated in a way that suggests untrustworthy metrics; what cost and latency does it add. When criteria change, version the rubric and keep consistency expectations. `[C04-013]`
11. **Use public benchmarks critically.** They shortlist, they do not choose. Before relying on one: does it measure the capability the application needs; is it recent and reliable; does the leaderboard's aggregation (plain average versus mean win rate) fit the weighting you need; are benchmarks in the set strongly correlated; is contamination plausible (n-gram overlap needs training data access; low perplexity is a cheaper, weaker signal). Prefer results reported on clean samples (the book's ideal is to disclose the contaminated share and report both full and clean scores). Check each benchmark's reliability, since anyone can publish one, and that scores on different scales are weighted deliberately. Build your own ranking from the benchmarks that match the task, then verify on your own set. Leaderboard compositions and model-behaviour studies in the book are dated. `[C04-010]`
12. **Write the findings.** Failures of a deterministic or functional check, rerun once, are candidates for `confirmed`. Judge-only, similarity-only with weak references, or small-sample results are `probable` or `unverified`, and the report states which.

| check | what is checked | how | evidence produced | type | criterion | how a failure is judged |
|---|---|---|---|---|---|---|
| EV-01 | Components and intermediate outputs identified; each has a check | read code and eval folders | component table | review | C04-011 | a component with no check, or only end-to-end scoring |
| EV-02 | Guideline has criteria, rubric with examples, threshold, out-of-scope rule | read the guideline or produce one with the user | guideline file | review | C04-012 | any element missing or ambiguous (two reviewers disagree on a sample) |
| EV-03 | Method matches criterion (table in step 3) | read eval code | mapping table | review | C04-013 | reference-based lexical metric with thin references, or judge used where a test could run |
| EV-04 | Functional correctness suite executes | run the project's tests or the generated runner via run_check.py | exec record, pass count | run | C03-010 | failing tests; judged per test case, not by aggregate alone |
| EV-05 | Exact or similarity scoring on the evaluation set | run the scorer via run_check.py | exec record, per-example scores | run | C03-011 | score below the guideline threshold; also check the false-accept risk of contains-matching |
| EV-06 | Embedding similarity sanity: similar pair scores above a dissimilar pair | run the embedding scorer on 3 hand-made pairs via run_check.py (needs approval if the embedding model is paid) | exec record | run | C03-012 | ordering violated, so the embedding is unsuitable for this data |
| EV-07 | Language-model metric report is valid where logprobs exist | read how perplexity or cross entropy is computed; check units, tokenizer and context length are stated | notes | review | C03-008 | cross-model comparison on bits per token; perplexity used as application quality; unit unstated |
| EV-08 | Contamination screen of a benchmark or eval set | perplexity comparison on the set versus fresh text (needs logprobs), or n-gram overlap if training data is accessible, via run_check.py; without either, `BLOCKED` and the item is `unverified` | exec record | run | C04-010 | the book's n-gram example is a sequence of 13 tokens shared with training data marking a sample dirty; for perplexity the book gives no threshold, so judge against the fresh-text baseline; result is `probable`, and a clean result is not proof |
| EV-09 | Judge configuration pinned and complete (model, prompt with task, criteria, scoring, examples, sampling) | read judge code | notes | review | C03-015 | any part unpinned, or prompt lacks examples |
| EV-10 | Judge reliability: same inputs scored twice, order swapped, length compared | run the judge on a small sample under the spend cap via run_check.py | exec records, agreement and order-effect figures | run | C03-016 | score disagreement between runs or after swapping order, or score tracking length, larger than the user can tolerate for the decision (no book threshold; state the tolerance beforehand); findings built on this judge capped at `probable` |
| EV-11 | Judge model choice and cost | read config; compute calls per example | notes, cost estimate | review | C03-017 | no rationale, or cost exceeds cap |
| EV-12 | Comparative run (A versus B) with randomised order and ties | run via run_check.py | exec record, win rate and match count | run | C03-019 | too few matches for the claimed margin, or a win rate presented as absolute quality |
| EV-13 | Comparison paired with a pointwise result | read the report | notes | review | C03-020 | decision rests on win rate alone |
| EV-14 | Evaluation set covers slices and size | count examples per slice | slice table | review | C04-013 | no out-of-scope or error-prone slice; set far below the sample sizes in step 5 |
| EV-15 | Bootstrap variance of the set | resample script via run_check.py | exec record, spread | run | C04-013 | wide swings: set too small to trust |
| EV-16 | Rerun reproducibility | run the full evaluation twice via run_check.py | two exec records | run | C04-013 | results differ beyond the stated tolerance (the book gives none; the user or an earlier baseline sets it) |
| EV-17 | Slice and aggregate results agree (Simpson check) | compute per-slice and overall | table | run | C04-013 | winner differs between slices and aggregate without explanation |
| EV-18 | Public benchmark use is justified | read the model-selection record | notes | review | C04-010 | benchmark irrelevant to the task, no contamination consideration, or used to pick rather than shortlist |

## Evidence and exit gate
- A run case is `PASSED` only with an exec record whose exit code is 0 and criterion met; a non-zero criterion result is `FAILED` with a rerun note. A runner crash or missing key is `BLOCKED`, not `FAILED`.
- Spend: record the cap, the approval and the actual calls. If no approval or no cap exists, the model-calling cases are `NOT_RUN` with that reason.
- Review checks stay `REVIEWED`.
- Exit when every criterion has a method, a result or a reason, the evaluation process has been audited (EV-14 to EV-17), and `python scripts/validate_report.py <run_dir>` prints 0 problems.

## Outputs
`results.json`, then [../../templates/findings-report.md](../../templates/findings-report.md); evaluation set and rubric go to the run folder, and an improved plan can be written with [../../templates/eval-plan.md](../../templates/eval-plan.md) if the user asks.

## Pitfalls
- Perplexity or benchmark scores reported as application quality `[C03-008]`, `[C04-010]`.
- Comparing bits per token across tokenisers `[C03-006]`.
- Lexical metrics penalising correct answers absent from the references `[C03-011]`.
- Unpinned judge, or judge changed between periods so a trend is an artefact `[C03-016]`.
- Judge scores read as accuracy; self-preference when the same model judges itself `[C03-016]`, `[C03-017]`.
- Declaring a winner from win rate without absolute quality `[C03-019]`.
- A guideline written after the scores `[C04-012]`.
- Single aggregate hiding slice failures `[C04-013]`.
